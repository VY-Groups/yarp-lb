# Distributed VIP admission (persistent Raft owner)

This extends the local VIP guard. A virtual socket can opt in with requireLocalAddressPresence=true, vipFleetId, vipQuorumConfigPath (absolute private file), and vipOwnershipEpoch (positive exact etcd modification revision). All sockets on that VIP must use the same parameters; the primary traffic and management IPs cannot be shared. Scope is uppercase SHA256 over UTF-8 gatewaycore-adc-vip-v1, LF, fleet ID, LF, canonical IP. The existing authenticated FleetQuorum transport uses three distinct pinned HTTPS Raft member identities, independent CA, and client mTLS. Use a unique client certificate/private key per gateway; the reader needs range-only rights to the dedicated /gatewaycore/adc-vip/v1/<scope> key. Never distribute one reader credential to two nodes.

The owner key is persistent (no TTL), created by an independent writer using create-revision CAS, with ASCII value vip_ followed by uppercase SHA256 of the owning client's DER certificate. The exact key mod_revision is the configured epoch. Expiring leases and malformed values are refused; the controlled writer below uses exact-state CAS transitions. Every poll must confirm the same state from a majority; loss of majority, wrong owner, wrong epoch, stale local sample or incomplete interface observations denies new requests before routing. A read timeout cannot extend the local freshness window. This is deliberately NOT automatic failover: transfer requires external owner isolation, confirmed address withdrawal, authenticated CAS ownership transfer, durable recovery, and supported host address manipulation. Do not delete or reassign this key just because a node stopped responding. Guarded in-flight requests are aborted on observed loss; see the in-flight revocation section. The shipping service never runs the local writer command or privileged address mutation. Keep the previous private listener configuration and use independently approved maintenance/rollback procedures; do not disable distributed admission while a peer may own the VIP.

The existing disposable real Raft fixture checks correct owner, wrong credential, wrong epoch/scope, single-member loss, and quorum loss. Local guard regression checks both authority and local address must be confirmed. Physical and automated takeover acceptance remain outstanding.

## Controlled ownership handoff

Use a separate, independently authorized writer host. The private writer settings add vipFencePublicKeyFile and vipFencePublicKeySha256 (uppercase SHA256 of the ECDSA P-256 SubjectPublicKeyInfo DER). Gateway reader settings must not contain these fields. Grant the gateway reader read-only access to its exact owner key. Grant the independent writer read/write access only to the exact owner and initialization keys, not a prefix or other modules. etcd write permission also permits delete: the trusted writer host and audit controls must prevent out-of-band deletion; the supported command never deletes either key. Keep the signing key outside the writer and gateway hosts. Use a separate certificate for the writer and each gateway. The writer can never select its own certificate as owner.

Invoke the shipping binary locally:

    dotnet GatewayCoreYarp.dll --vip-owner <writer-config> <scope> status
    dotnet GatewayCoreYarp.dll --vip-owner <writer-config> <scope> revoke <old-certificate-sha256> <old-epoch>
    dotnet GatewayCoreYarp.dll --vip-owner <writer-config> <scope> activate <old-certificate-sha256-or-dash> <revoked-epoch-or-zero> <new-certificate-sha256> <expiry-unix-seconds> <absolute-signature-file>

Revocation CAS replaces the active value with a persistent vip_revoked_ record. Do not delete the record. Both nodes are denied while revoked. After confirmed physical isolation/withdrawal and termination of old in-flight traffic, an independently authorized fencing authority may sign the exact UTF-8 message (LF-separated, no final newline): GatewayCore.VIP.HardFence.v1, scope, old certificate pin (or dash for independently verified first provisioning), revoked epoch (or zero), new certificate pin, expiry Unix seconds. Use ECDSA SHA256 with DER signature; expiry must be within five minutes. The command verifies trust, signature, epoch and predecessor, then CAS-activates the successor and confirms the resulting revision by authenticated majority. Provision the new exact epoch in its listener config using reviewed host procedures. No automatic ownership transfer occurs on timeout. If any command returns unconfirmed, inspect status; never delete the key or force a takeover. A valid signature attests to externally verified hard fencing; it does not itself perform fencing or prove the external authority did its job. The existing old epoch is rejected after revocation on fresh observation. Automatic hard-fence provider, host address actions, in-flight drain, persistent orchestrator and recovery remain necessary.

First activation atomically creates a persistent initialization marker at the owner key plus /initialized. If the owner record is subsequently missing but the marker survives, bootstrap and status refuse recovery rather than allowing reuse. Protect and back up both keys; deletion or rollback of the entire Raft state is outside this local replay defense and requires independent recovery. The gateway reader remains read-only. The real fixture uses separate client-only successor credentials, not a Raft server key.

## Local host address actuator

On each separately administered gateway, provision a dedicated up IPv4 interface without a default gateway or management address, a private durable journal directory, and a reviewed isolated listener configuration containing the exact current VIP epoch and unique reader credential. The local elevated command uses the host's YARP_LISTENERS_CONFIG_FILE; it does not accept arbitrary IP addresses or shell commands.

    dotnet GatewayCoreYarp.dll --vip-address <private-journal-directory> <virtual-service-id> <exact-interface-id> status
    dotnet GatewayCoreYarp.dll --vip-address <private-journal-directory> <virtual-service-id> <exact-interface-id> assign
    dotnet GatewayCoreYarp.dll --vip-address <private-journal-directory> <virtual-service-id> <exact-interface-id> withdraw

Assignment requires a fresh exact authenticated owner check before changing the OS, records a durable intent, confirms the kernel /32 and checks authority again. Withdrawal is allowed without quorum but only for a journal-confirmed assignment; it never adopts an existing address. A lost authority check triggers attempted withdrawal. On Linux the tool uses iproute2 with noprefixroute; on Windows it uses the fixed NetTCPIP cmdlets with ActiveStore, SkipAsSource and a DHCP-disabled interface. It does not persist a static address in the OS or change routes. The journal serializes cooperating operations. An incomplete assign-intent is deliberately not automatically adopted or deleted: hard-fence the host, inspect and reconcile independently. A confirmed withdrawn entry may only be followed by a newer ownership epoch. Back up the journal without restoring stale records. Keep the journal directory and installed binary accessible only to the approved privileged operator. Do not perform competing out-of-band address changes. Stop or drain the old gateway before transfer; configure the new epoch and assign before starting the successor listener (Kestrel binds actual IPs). The real CI address test runs in a fresh disposable Linux network namespace; Windows live NetTCPIP acceptance, automatic orchestration, external fencing and IPv6 actuator are not claimed.

## In-flight traffic revocation

Guarded requests have bounded lifetime tracking (4096 concurrent requests per virtual socket, including streams). An independent 250 ms watchdog sweeps expired observations even if the polling task stalls. On ownership denial, local address withdrawal, stale or invalid observation, or gateway shutdown, the gateway aborts affected in-flight HTTP transports and refuses new traffic with 503. Completion frees the tracking slot; the UI shows live tracked request counts. This is fail-closed interruption, not graceful draining or proof that an upstream side effect has been canceled. Before planned transfer, stop admission and independently verify old traffic is drained and the old host hard-fenced. No claim is made for cancellation of already committed backend transactions, L4 or a stalled process watchdog. The live isolated socket fixture withdraws its temporary IP during a streaming response and requires the actual stream to terminate early.

## Planned graceful drain

In Infrastructure inventory, an Administrator may select Drain VIP on a dedicated address where every virtual socket is guarded. Enter the change reason. The authenticated CSRF-protected API uses the existing resource mutation audit/change-freeze controls and persists the address-wide drain flag before applying it to all sockets. A drain stops new admissions while healthy in-flight requests finish; ownership loss, stale observations and shutdown still abort the affected transports. Refresh the inventory until all guarded request counters for that address are zero. That is local pipeline evidence, not proof of upstream transaction completion or physical isolation. Resume VIP is a separate audited administrator operation and requires current local/quorum authorization. The flag persists across restart; an invalid, unknown or duplicate persisted address refuses startup rather than losing the drain. Do not edit the private state file while the service runs. This is not automatic peer orchestration or hard fencing. Tests cover persisted state, drain/reopen semantics and real HTTP API role/validation rejection; positive isolated socket administrator workflow acceptance remains required.

## IPv6 host address lifecycle

Canonical global-unicast and unique-local IPv6 VIPs use exact /128 assignment and the IPv6 interface index. Scoped, mapped, multicast and link-local addresses are refused. Linux uses ip -6 with noprefixroute; Windows uses the fixed IPv6 NetTCPIP ActiveStore commands on a dedicated DHCP-disabled interface. Assignment waits for preferred address readiness (Linux kernel flags or Windows DAD state), and local admission denies observed non-ready IPv6 addresses. Unknown readiness denies traffic. A DAD timeout leaves an uncertain durable intent for independent recovery; it is not permission to adopt or force-delete an address. Disposable Linux namespace and pure flag tests are added; Windows live mutation, external hard fencing, automated peer takeover, and physical neighbor convergence still require acceptance.

## Independent HTTPS hard-fence provider handoff

On the isolated writer host only, configure a separate owner-private JSON file with origin (HTTPS root URL), leafSha256, caFile, certFile, keyFile, scope and ownerPins (exact two gateway certificate pins). Use a separate provider client identity and pinned independent CA/leaf. The provider must map the configured scope and old pin to a real, durable physical isolation mechanism that prevents reactivation; no signing key or arbitrary shell command is passed. Provider endpoint POST /v1/vip/hard-fence accepts scope, oldPin, revokedEpoch, newPin and returns HTTP 200 with the same four fields, expires (Unix seconds) and signature (canonical base64 DER ECDSA permit matching the existing signing contract). The provider must revalidate hard fencing on repeat requests and must never sign if isolation cannot be verified. Provider implementation/deployment and hardware validation are external prerequisites; a signed response alone is not proof that the provider actually isolated hardware.

    dotnet GatewayCoreYarp.dll --vip-owner <writer-config> <scope> transfer <old-pin> <old-epoch> <new-pin> <provider-config>
    dotnet GatewayCoreYarp.dll --vip-owner <writer-config> <scope> resume-transfer <old-pin> <revoked-epoch> <new-pin> <provider-config>

The command first verifies the exact active revision, revokes by CAS, confirms the persistent revoked state, then requests a signed permit over mTLS. Only a matching fresh response and the existing independent signature verification permit successor activation. Any failure leaves the ownership denied or unconfirmed; observe before explicit resume, never force rollback. This does not automatically decide failure, provision the successor address/listener epoch, or start services. Pure negative contract tests cover failed provider, exact resume and mismatched permit; live provider, multi-host failover and physical acceptance remain outstanding.

### Distributed runtime address validation and planned drain acceptance

A distributed VIP must be observed exactly once with the actuator's /32 or /128 prefix on a non-loopback, non-tunnel, up interface without a default gateway. A confirmed quorum owner does not override invalid local address state. A real isolated socket fixture exercises administrator mTLS bootstrap, CSRF rejection, address-wide drain across two sockets, completion of admitted streams, zero active counts, process restart with persistent drain, and explicit resume, followed by emergency withdrawal. These tests do not replace external hardware or multi-host acceptance.

## Journal-bound successor activation

For independently managed automatic ownership transitions, omit vipOwnershipEpoch and set vipJournalDirectory (absolute protected directory) and vipInterfaceId (exact dedicated interface identity) on every socket of the same VIP. The gateway startup binds to the confirmed local journal epoch; it never follows a new revision inside an existing process. Use `--vip-address <directory> <service-id> <interface-id> reconcile` on the independently administered local host. A fresh authenticated Raft observation identifies whether this node owns the current revision. Reconcile withdraws only journal-owned addresses on revocation or change of epoch, assigns only after exact current ownership, and rechecks ownership after mutation. Same-epoch recovery of an absent address is allowed only with a confirmed assigned journal and fresh ownership. Uncertain intent, stale revision, unmanaged address and missing quorum refuse mutation. The command reports eligibleToStart only for the confirmed journal-bound assignment. Before starting the service verify this field and exit code; start the gateway as a new process. The service must have read-only access to the protected journal; the privileged actuator requires write access and OS address privileges. Do not run the gateway service with unnecessary privileges. Journal and kernel readiness are checked before and after each runtime quorum poll; any changed journal epoch denies traffic until a new process is launched. Real external node service supervisor, autonomous writer policy, and physical neighbor convergence still require integrated acceptance.

## Automatic writer policy and durable recovery

On the independent single writer host only, run `--vip-owner <writer-config> <scope> automatic <preferred-pin> <other-pin> <provider-config> <protected-journal-file> failback-on|failback-off`. Use a dedicated private directory and exclusive single process; protect its Windows ACL or Linux owner permissions. The controller polls every five seconds. Three consecutive unhealthy owner samples spanning at least ten seconds and an eligible peer are required for failover. Failback is opt-in, requires a healthy current owner, preferred peer eligible for two minutes and five minutes of stable ownership, then independently confirmed drain. Unknown, non-quiescent, stale or unavailable evidence resets thresholds. Each transition records a durable intent before any mutation. Revocation, independent fencing permit verification, quorum successor activation and provider-confirmed serving state are required before completion. Restart with a pending transition refuses automatic mode; use `recover-automatic` with the same arguments after independent reconciliation. Recovery resumes only the exact predecessor/revoked/successor state and never deletes quorum records. Do not run multiple writers or manually change ownership outside the controller journal.

Provider must additionally implement authenticated POST `/v1/vip/node-status`, `/v1/vip/drain-node`, `/v1/vip/activate-node`. Request fields: scope, ownerPin, epoch, otherPin, nonce. Response must echo all five and include ownerServing, otherEligible, ownerDrained, quiescent. The provider must independently check the exact quorum revision before all mutations, perform real health/eligibility probes, prevent old data-plane access until a separately authorized successor action, serialize idempotent actions, and only report quiescent after no action remains outstanding. Activation must invoke local journal-bound reconcile and start the new process, then independently verify actual client traffic. A timeout or unsupported endpoint refuses progression; never substitute a fabricated response. The current code provides the authenticated controller side, journal and policy, not a site-specific hardware provider server. Actual provider implementation, service supervision and real two-node acceptance remain required.

## Redfish independent physical power fencing adapter

The shipped binary now also supports `--vip-redfish-provider <protected-config>` on a separately administered private host. This is a real HTTPS mTLS hard-fence endpoint for Redfish-capable BMCs, not a mock permit issuer. Configure `listenIp`, `port`, `scope`, `readerConfig` (separate read-only Raft credential), `serverPfx`, `serverPasswordFile`, `writerCaFile`, `writerPin` (SHA256 DER), `signingKeyFile` (private P-256 PEM), and exactly two `nodes` with `pin` and `bmc`. Each BMC config contains `origin` (HTTPS root), `leafSha256`, `caFile`, `systemPath` (exact /redfish/v1/Systems/ID), `systemUuid`, and `credentialFile` (private JSON username/password). The BMCs must be distinct; each must advertise ForceOff and report PowerRestorePolicy AlwaysOff before the provider will power off an active server. Disable all competing power-on automation and restrict BMC credentials to the authorized provider; changing the restore policy or powering a server back on is outside this endpoint. Use separate BMC and management networks. The provider verifies the persistent revoked Raft revision before mutation, verifies the actual Off state twice, and signs a short-lived exact-revision permit only after rechecking quorum. No success is inferred from HTTP 2xx alone. Unsupported BMCs, TLS mismatch, unknown state, timeout and loss of quorum refuse a permit. The independent controller's node-status/drain-node/activate-node supervisor integration remains a separate prerequisite for unattended takeover and failback; do not route those actions to this power-fencing-only endpoint or enable automatic mode until the full provider is commissioned. Real BMC/Windows/Linux integration and issue #36 physical acceptance remain unverified.

### Resource-aware admission polling

Sockets sharing one validated VIP authority use a single quorum probe per one-second observation cycle and one local address scan per configured IP. Distinct address/authority combinations are never coalesced. The two-second poll deadline, three-second freshness bound and 250 ms watchdog remain unchanged. Healthy watchdog sweeps avoid allocating a list of active requests. Cancellation denies the sample. For N sockets on one VIP, the majority-read fanout is reduced from N groups of three requests to one group of three, not a weaker quorum. This is a structural reduction, not a measured throughput claim; benchmark on the actual target hardware and retain physical acceptance.

## Local node lifecycle supervisor

Use the protected local `--vip-node <config> activate <exact-epoch>` command on the selected gateway host under its separate privileged operator/service-supervisor account. Config contains scope, serviceId, serviceName (GatewayCoreYarp on Windows; exact approved .service unit on Linux), listenerConfig (protected absolute reviewed JSON), probePath (actual idempotent application GET path), probeCaFile, probeLeafSha256, probeBodySha256 (SHA256 of exact successful response body). Use a dedicated single-address instance; the target service must already be installed, configured with the same listener file and restricted runtime identity, and disabled from automatic startup outside the independent supervisor. The application probe is direct to the HTTPS VIP, requires a valid IP SAN plus pinned chain and exact body. The command confirms exact quorum epoch before reconciliation, before and after service start, and after real application readiness. On an unsuccessful activation it attempts service stop and journal-owned withdrawal with independent compensation deadlines, and returns failure if either cannot be confirmed. `stop-withdraw <exact-epoch>` is for the current local journal epoch only; use after an approved drain or hard-fence decision, not as a substitute for graceful draining. On failure retain journal and independently reconcile. A withdrawal at the current epoch intentionally requires a new authorized epoch to assign again. The fixed service commands do not accept shell source or network-supplied targets. Contract tests cover stale epoch refusal, activation ordering and compensation. The remote independent provider's node-status/drain/activate wiring and real Windows/Linux supervised failover acceptance remain separate gates.

### Independent machine-authenticated drain

Set GATEWAYCORE_VIP_DRAIN_CLIENT_SHA256 to the dedicated machine client certificate SHA256 pin and GATEWAYCORE_VIP_DRAIN_SCOPE to the exact journal-bound VIP scope. Enroll its certificate in the isolated management mTLS allowlist and restrict its source network. POST /admin/vip-machine/drain with scope, epoch, nonce (64 uppercase hexadecimal characters), drain (true requests drain, false reads status). This narrow endpoint never grants an administrator session; it checks the exact current quorum epoch, local admission, configuration freeze, applicable license and external audit receipt/outbox before persisting a drain. It does not clear human maintenance drains. Automatic drain is epoch-bound and survives restart at that epoch. A newer authorized epoch ignores the old automatic drain; manual drain remains in force. The network inventory distinguishes manual and automatic drains, configured automation and ownership epoch. Remote transport and full failover acceptance require additional integration.

### Remote supervisor and drain transport

The independent Redfish provider accepts optional agent and drain client settings on both nodes (origin, leafSha256, caFile, certFile, keyFile). On each node run --vip-node-agent with a private JSON file containing scope, nodePin, otherPin, readerConfig, supervisorConfig and server (listenIp, port, pfx, passwordFile, clientCaFile, clientPin). The node agent uses the exact supervisor configuration and local reader identity; it exposes only status and activate to the pinned independent provider. Provision the dedicated supervisor service disabled at boot on Linux, Manual and Stopped on Windows. Provider status checks standby eligibility (no VIP, no unresolved journal, stopped dedicated service) and owner application readiness, and separately queries authenticated drain state. Planned failback requires the peer eligible, a committed automatic drain and zero in-flight requests. Unknown health, missing certificates, wrong epochs and incomplete drain fail closed. Before remote activation the provider rechecks that the predecessor is powered off, then checks again after activation. A fenced node must be brought back as a non-serving standby by authorized site personnel before it becomes eligible for automatic failback; this adapter does not automatically power on fenced hardware. Keep the BMC and management networks isolated and disable competing service/power automation. Current source changes require exact-head CI and independent review; no live two-node hardware result is asserted.

Recovery safety: failback always rechecks the authenticated drain endpoint until the active count is zero, even when a persisted drain is already reported. The node supervisor passes the expected epoch into the address actuator and refuses delayed compensation against a newer journal. The runtime retains same-epoch automatic drains even if machine endpoint configuration is removed. Operator resume affects only manual drain; independently authorize a newer ownership epoch to clear automatic drain.

### Combined lifecycle integration fixture

The Windows/Linux fencing contract CI includes a disposable loopback HTTPS server with generated CA and separate client identities. It runs the same provider action decision and automatic transition code used by the product; checks valid mTLS, wrong client/server pin, stale epoch, interrupted hard fencing, successor startup failure, journal restart recovery, manual maintenance denial and completion of a recovered failback only after zero active requests. Raft and BMC state in this fixture are simulated; it does not replace the existing real Raft tests or actual OS/BMC two-host acceptance. No production credentials or BMCs are contacted.

The combined fixture also exercises the actual pinned VipMachineTransport on provider-to-node and provider-to-drain loopback requests. Node identities, BMC and Raft are fixture state; production uses separately pinned management origins. A manual resume is not offered for an automatic-only drain; the inventory shows that an independently authorized ownership transition is required.
