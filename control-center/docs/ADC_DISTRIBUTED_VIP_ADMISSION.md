# Distributed VIP admission (persistent Raft owner)

This extends the local VIP guard. A virtual socket can opt in with requireLocalAddressPresence=true, vipFleetId, vipQuorumConfigPath (absolute private file), and vipOwnershipEpoch (positive exact etcd modification revision). All sockets on that VIP must use the same parameters; the primary traffic and management IPs cannot be shared. Scope is uppercase SHA256 over UTF-8 gatewaycore-adc-vip-v1, LF, fleet ID, LF, canonical IP. The existing authenticated FleetQuorum transport uses three distinct pinned HTTPS Raft member identities, independent CA, and client mTLS. Use a unique client certificate/private key per gateway; the reader needs range-only rights to the dedicated /gatewaycore/adc-vip/v1/<scope> key. Never distribute one reader credential to two nodes.

The owner key is persistent (no TTL), created by an independent writer using create-revision CAS, with ASCII value vip_ followed by uppercase SHA256 of the owning client's DER certificate. The exact key mod_revision is the configured epoch. Expiring leases and malformed values are refused; the controlled writer below uses exact-state CAS transitions. Every poll must confirm the same state from a majority; loss of majority, wrong owner, wrong epoch, stale local sample or incomplete interface observations denies new requests before routing. A read timeout cannot extend the local freshness window. This is deliberately NOT automatic failover: transfer requires external owner isolation, confirmed address withdrawal, authenticated CAS ownership transfer, durable recovery, and supported host address manipulation. Do not delete or reassign this key just because a node stopped responding. Existing in-flight requests are not revoked. The shipping service never runs the local writer command or privileged address mutation. Keep the previous private listener configuration and use independently approved maintenance/rollback procedures; do not disable distributed admission while a peer may own the VIP.

The existing disposable real Raft fixture checks correct owner, wrong credential, wrong epoch/scope, single-member loss, and quorum loss. Local guard regression checks both authority and local address must be confirmed. Physical and automated takeover acceptance remain outstanding.

## Controlled ownership handoff

Use a separate, independently authorized writer host. The private writer settings add vipFencePublicKeyFile and vipFencePublicKeySha256 (uppercase SHA256 of the ECDSA P-256 SubjectPublicKeyInfo DER). Gateway reader settings must not contain these fields. Grant etcd read and transaction rights only for the exact dedicated VIP key; never grant delete or prefix-wide write privileges. Keep the signing key outside the writer and gateway hosts. Use a separate certificate for the writer and each gateway. The writer can never select its own certificate as owner.

Invoke the shipping binary locally:

    dotnet GatewayCoreYarp.dll --vip-owner <writer-config> <scope> status
    dotnet GatewayCoreYarp.dll --vip-owner <writer-config> <scope> revoke <old-certificate-sha256> <old-epoch>
    dotnet GatewayCoreYarp.dll --vip-owner <writer-config> <scope> activate <old-certificate-sha256-or-dash> <revoked-epoch-or-zero> <new-certificate-sha256> <expiry-unix-seconds> <absolute-signature-file>

Revocation CAS replaces the active value with a persistent vip_revoked_ record. Do not delete the record. Both nodes are denied while revoked. After confirmed physical isolation/withdrawal and termination of old in-flight traffic, an independently authorized fencing authority may sign the exact UTF-8 message (LF-separated, no final newline): GatewayCore.VIP.HardFence.v1, scope, old certificate pin (or dash for independently verified first provisioning), revoked epoch (or zero), new certificate pin, expiry Unix seconds. Use ECDSA SHA256 with DER signature; expiry must be within five minutes. The command verifies trust, signature, epoch and predecessor, then CAS-activates the successor and confirms the resulting revision by authenticated majority. Provision the new exact epoch in its listener config using reviewed host procedures. No automatic ownership transfer occurs on timeout. If any command returns unconfirmed, inspect status; never delete the key or force a takeover. A valid signature attests to externally verified hard fencing; it does not itself perform fencing or prove the external authority did its job. The existing old epoch is rejected after revocation on fresh observation. Automatic hard-fence provider, host address actions, in-flight drain, persistent orchestrator and recovery remain necessary.
