# GatewayCore offline commercial licensing — isolated development

**DO NOT MERGE TO MAIN. Owner-directed draft feature branch. No release authorization.**
This is the initial verification SDK, not a complete license system and not wired into the running product. The existing product and release behavior are unchanged.

## Fixed constraints
- Customer installations must activate, validate, renew, upgrade, recover and operate with zero internet connectivity and no license heartbeat or mandatory telemetry.
- No HSM, TPM, dongle or additional hardware dependency. Windows and Linux; physical and VM support by design, subject to acceptance.
- Company-only issuer in a separate private system. Customer packages contain only pinned public verification keys, never production private signing material.
- No universal license, unsigned fallback, frontend-only authorization or hidden bypass.
- No license-server dependency or expensive signature checks in the per-request data path. Invalid fresh installs cannot activate; existing traffic safety and emergency recovery require a separate explicit policy and integration tests.

## Implemented in phase 1
Dependency-free .NET 10 verification SDK and dedicated Windows/Linux CI. GCL1 is an exact ASCII compact envelope: GCL1.keyId.base64url(payload).base64url(signature). Signature is ECDSA P-256 SHA-256 IEEE P1363 (64 bytes) over the first three segments verbatim, including format and key ID. The payload is UTF-8 JSON, with a closed schema, bounded size/depth, unique keys, strict types, integer Unix UTC timestamps, uppercase SHA-256 installation public-key digest, unique explicit feature list, subscription limits, allocation ID and revision. Exact signed payload bytes are used for the checkpoint digest; no JSON reserialization. Pinned keys are injected by a trusted caller; no key is trusted from the file itself. The test harness uses ephemeral signing keys only.

Verification authenticates entitlement contents and matches a caller-provided installation-key digest. It evaluates validity using caller-provided time and compares an optional previous checkpoint. It does NOT create installation keys, prove local key possession, enforce a fleet seat count, persist a revision floor, detect clock rollback or protect against administrator-level code patching. The caller must implement those controls. The verifier is not connected to runtime configuration or management APIs. Expired and future licenses never grant active entitlements in this SDK.

## Phase 2 — local activation and state
Added explicit provisioning, P-256 installation identity and signed GCR1 activation requests (public SPKI and random request ID, proof of possession). Windows encrypts the private key using user-scope DPAPI, so the installer must provision the final service account and ACLs; Linux uses a 0700 service directory and 0600 files, with no claim of encryption at rest. A signed state envelope stores the exact license and observed time floor, protected by an exclusive local file lock and flushed temporary-file replacement. Imports require active signed entitlements and the same customer/deployment/allocation; stale or equivocal revisions, edited state and significant observed time rollback are denied. Missing or interrupted state never regenerates a key silently. Tests exercise activation, restart, renewal, tamper, independent-install copy refusal and observed rollback. No power-loss or whole-directory snapshot rollback guarantee, no hard-link or hostile-root containment claim; the provisioned local directory and parent ACLs must be trusted. The issuer must durably deduplicate request IDs, and actual service provisioning/recovery and runtime integration remain pending.

## Phase 3 — issuer prototype
The isolated company-side tools/LicenseAuthority project has a local CLI and issuer library, with encrypted PKCS#8 PEM loading, operator-approved subscription terms, proof-of-possession request validation, per-subscription seat/site limits, persisted allocation IDs and monotonic renewals. A single filesystem lock commits allocation and issued bytes together; exact request retry returns the original output without spending another seat. No real signing key is committed. Never ship this project in customer packages. The ledger is a private, single-authority prototype, not a production PostgreSQL portal, MFA/dual-approval system or resilient key-management service. No revocation or reassignment implemented. Operator-managed ACLs, backed-up authoritative ledger and separate private deployment remain required. E2E tests use ephemeral keys and exercise real issuance and import, second-node allocation, excess seat/site denial and renewal.

## Phase 4 — irreversible offline revocation
GCV1 is a separately signed, bounded allocation-specific revocation document. The issuer commits the document and permanently marks that allocation revoked, refuses further issuance or renewal, and does not free a seat merely because it issued a revocation. The customer imports the exact signed file; the verifier checks the issuer trust root and all allocation/customer/deployment/installation bindings. The signed state persists revocation atomically with the current license; active entitlements are denied across restart and later imports. Forged or cross-allocation revocation leaves the current entitlement unchanged. No remote enforcement or full-snapshot rollback guarantee. Reallocation, issuer key rotation, private portal and safe runtime expiry/DR remain outstanding.

## Phase 5 — commercial gateway integration prototype
A separate compile-time GatewayCoreCommercial=true profile requires an owner-supplied embedded public trust JSON (key ID to base64 SPKI). Normal development builds do not reference the SDK or activate licensing; they are not commercial deliverables. No runtime flag disables the gate in the commercial binary. The local --license-init command provisions the installation identity under the existing private control-plane directory. License Center UI and authenticated API export requests, import licenses/renewals and signed revocation. Mutations retain the existing CSRF, role and step-up checks. Unlicensed management requests return 402; a fresh process denies YARP forwarding until L7 is authorized. The process retains previously admitted forwarding after expiry/revocation to avoid an immediate traffic outage; this prototype does NOT fence external config reload, guarantee safe restart or qualify DR. Feature gates cover fleet/HA, GitOps, TLS and audit API families only; topology constraints, independent engines, direct configuration paths, exact feature gating, protected startup, EULA/privacy integration and real shipping commercial browser/traffic acceptance remain open. Dedicated CI compiles the commercial profile with a disposable public key; no private key in customer artifacts. PR #545 remains a separate dependency and has not been merged here.

## Phase 6 — no-egress commercial process acceptance fixture
The Linux CI job builds the actual commercial gateway against an ephemeral test public trust resource and creates a disposable issuer in a private runner directory. After build, the fixture executes inside a network namespace with only loopback and no route; it exercises the shipping Kestrel/YARP process and real issuer on activation request, invalid signature/CSRF denial, pre-activation API and proxy denial, licensed access, unlicensed fleet denial, restart, renewal, rollback rejection, offline revocation, running traffic continuity and fresh revoked-process denial. This fixture is source committed; CI must pass before claiming results. No private test key is uploaded or included in product output. Windows commercial compilation and SDK fixtures remain distinct from live Windows service qualification.

## Phase 7 — signed binary inventory verifier
Added GCM1 signed immutable-package inventory verification, with separately pinned release-signing public keys, full source commit binding, strict paths and bounded JSON, exact file inventory and streaming SHA-256 checks. Tests cover modified/missing/injected binaries, signed traversal attempts, wrong release source, and rejection of an entitlement-signing key as release trust. This verifier is a reusable SDK component only; it has not yet been integrated into an enforced commercial package startup or installer. Authenticode, Linux packaging, selective obfuscation and external code execution policy remain outstanding. It does not protect against privileged patching of the verifier itself or live file replacement after verification.

### Independent review correction
A signed currently active renewal which removes L7 immediately fences new proxy admission (503), reports feature-restricted, and locks ordinary management. Existing in-flight requests are not aborted. A subsequent signed active upgrade can restore admission. This is distinct from unexpected expiry or revocation continuity and the decision is applied from the exact committed import result, without a second state read. Added real no-egress downgrade/upgrade regression and corrected the fixture's shadowed local variable.

### Real HTTP regression correction
The Linux no-egress fixture reached the actual gateway and caught an ASP0016 route-handler overload defect: a Task<IResult> lambda selected RequestDelegate, silently discarding HTTP error/success results. The import and revoke routes now explicitly use the Delegate route-handler overload; commercial builds treat ASP0016 as an error. Existing expected HTTP statuses are unchanged. Repeat exact-head real-process acceptance required.

## Signed commercial publish and pre-start package verification
Commercial publishing requires GatewayCoreReleasePackage=true, GatewayCoreReleaseTrustFile and the exact lowercase GatewayCoreReleaseSourceCommit in addition to the commercial entitlement trust. Release and entitlement public keys must be distinct. The published executable validates the entire GCM1 package inventory before any local provisioning command or listener starts; a missing, tampered or injected package file returns exit 78. --verify-release is a non-mutating local check. Development-only commercial builds remain available for CI but cannot be published through the commercial publish target without the release profile. Tests publish actual Windows/Linux binaries using disposable separate trust keys and exercise missing manifest, valid package, injected and modified asset rejection. Release signing operation and deployment custody must be implemented in the company-side repository and protected external key storage. This does not prevent privileged binary replacement or post-start tampering. No commercial release authorized.
