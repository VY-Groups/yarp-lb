# Opt-in Linux distributed Data Protection repository (software integration)

Set YARP_LINUX_DP_DISTRIBUTED_RING_CONFIG to a separately provisioned private absolute JSON path outside the service state. All three HTTPS endpoints have an independent root CA and distinct approved leaf SHA-256 and Raft member IDs. The wrapping certificate remains separate from the mTLS identity. The local key directory must be empty; no local/offline recovery or replica setting may coexist. Use a private PFX and separate password file for mTLS, distinct from the wrapping certificate. This is single-tenant and opt-in; standalone mode is unchanged.

JSON property names: Fleet, NodeId, ClusterId (decimal string), MinimumRaftRevision (positive integer), Members (three objects with Url, LeafSha256, MemberId decimal string), Mode ("reader" or "writer"), WriterNode, LeaseId, WriterModRevision (writer only; null for reader), CaPath, ClientPfxPath, ClientPasswordPath. Writer lease values must come from independently issued runtime authority under /gatewaycore/linux-dp/runtime-writer/<fleet>. The operator must provision narrow etcd RBAC independently; a reader must have no mutation permission, and writer identity must only have its authorized fleet ring scope. TLS leaf pin rotation and offline revocation are operator controlled; chain revocation checks are not online.

Actual IXmlRepository reads bounded encrypted key XML with two matching linearizable distinct-member observations. Only approved wrapping recipients are accepted. Writes are create-only transactions checking the independently pinned runtime lease and mod revision. No automatic key generation (even writer); explicit IKeyManager rotation is needed. No local fallback or retry of uncertain writes. Revocation XML is deliberately refused, so this is not yet a complete revocation/lifecycle protocol. Fresh processes use the provisioned minimum Raft revision; persist and advance that externally before any restore/reconfiguration. The reader may retain the framework's normal cached key ring; coordinated activation and cache refresh, remote private-key custody, lease renewal/promotion and actual HTTP product traffic remain separate gates. The new .NET fixture uses synthetic Raft responses with actual encrypted keys and cookies. It does not constitute real three-member .NET acceptance or release qualification. Do not enable in production before complete #48 acceptance.
