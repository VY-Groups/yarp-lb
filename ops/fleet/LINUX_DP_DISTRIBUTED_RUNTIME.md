# Opt-in Linux distributed Data Protection repository (software integration)

Set YARP_LINUX_DP_DISTRIBUTED_RING_CONFIG to a separately provisioned private absolute JSON path outside the service state. All three HTTPS endpoints have an independent root CA and distinct approved leaf SHA-256 and Raft member IDs. The wrapping certificate remains separate from the mTLS identity. The local key directory must be empty; no local/offline recovery or replica setting may coexist. Use a private PFX and separate password file for mTLS, distinct from the wrapping certificate. This is single-tenant and opt-in; standalone mode is unchanged.

JSON property names: Fleet, NodeId, ClusterId (decimal string), MinimumRaftRevision (positive integer), Members (three objects with Url, LeafSha256, MemberId decimal string), Mode ("reader" or "writer"), WriterNode, LeaseId, WriterModRevision (writer only; null for reader), CaPath, ClientPfxPath, ClientPasswordPath. Writer lease values must come from independently issued runtime authority under /gatewaycore/linux-dp/runtime-writer/<fleet>. The operator must provision narrow etcd RBAC independently; a reader must have no mutation permission, and writer identity must only have its authorized fleet ring scope. TLS leaf pin rotation and offline revocation are operator controlled; chain revocation checks are not online.

Actual IXmlRepository reads bounded encrypted key XML with two matching linearizable distinct-member observations. Only approved wrapping recipients are accepted. Writes are create-only transactions checking the independently pinned runtime lease and mod revision. No automatic key generation (even writer); explicit IKeyManager rotation is needed. No local fallback or retry of uncertain writes. Revocation XML is deliberately refused, so this is not yet a complete revocation/lifecycle protocol. Fresh processes use the provisioned minimum Raft revision; persist and advance that externally before any restore/reconfiguration. The reader may retain the framework's normal cached key ring; coordinated activation and cache refresh, remote private-key custody, lease renewal/promotion and actual HTTP product traffic remain separate gates. The new .NET fixture uses synthetic Raft responses with actual encrypted keys and cookies. It does not constitute real three-member .NET acceptance or release qualification. Do not enable in production before complete #48 acceptance.

## Real network acceptance fixture

The existing three-member etcd CI now builds the actual .NET test executable and uses it with the product LinuxKeyProtection.Configure path, separate state roots, independently provisioned wrapping-certificate copies and pinned TLS endpoints. It checks actual encrypted XML in Raft, cross-process old/new cookie decryption, rejected reader and revoked/stale writer writes, independent epoch change and minority startup refusal without local fallback. The fixture does not implement RBAC reassignment, production secret delivery, renewal, or uninterrupted live routing. All tests are disposable and CI-only.

## Exact writer identity and mutation fence

All runtime configurations now require `ClientLeafSha256` (uppercase SHA-256 of the independently approved client certificate DER); writers additionally require `WriterRecordSha256` (uppercase SHA-256 of the exact independently approved runtime authority record bytes, null for readers). Obtain the latter from the independent issuer's verified record, not by trusting an arbitrary received record. Before each write two distinct pinned Raft members must confirm that exact record, designated node, lease and modification revision. A reachable contradictory member vetoes mutation. The actual ciphertext write also compares the exact record VALUE, lease, mod revision and key absence in one transaction. No automatic epoch adoption or retry. Real fixture covers wrong client pin, wrong writer record, stale writer and new epoch; synthetic regression checks revocation at commit. This remains dependent on narrow external RBAC and operator-approved renewal; does not itself grant writer authority or complete release acceptance.

## Combined delivered wrapping credential and real distributed key-ring acceptance

The real Raft/.NET fixture now creates one source PFX and two distinct recipient encryption identities, invokes the actual signed/encrypted custody CLI in separate subprocesses for each, rejects a different recipient private key and replay, and checks owner-private received outputs. Source PFX, password and original wrapping private key are removed before either runtime starts. The actual .NET key repository then uses only the received credential paths for real ciphertext creation and cross-node cookie reads through real Raft, writer revocation/rollover and minority startup denial. The disposable runner uses one OS account, and it does not prove remote network transport, production RBAC, hardware custody, durable external delivery floor or combined product traffic cutover. #535 is an integration dependency.

## Shipping operator key issuance

The shipping Linux executable now supports `dotnet GatewayCoreYarp.dll --linux-dp-key-issue bootstrap` for a new empty distributed ring and `dotnet GatewayCoreYarp.dll --linux-dp-key-issue stage 2027-01-01T00:00:00Z` for a separately approved future activation (example UTC format only; must be 48 hours to 7 days ahead at execution). Supply the independent writer settings and wrapping certificate via the existing protected environment/file configuration; no password/secret arguments. This starts no HTTP listener. Bootstrap compares the entire ring prefix for absence in the same fenced Raft transaction. Stage requires an existing nonrevoked active key surviving the activation and refuses a second future generation. The stage check is a precheck, not a separate distributed serialization primitive: coordinate a single operator process per writer epoch. A failed/uncertain operation requires independent inventory reconciliation, not automatic retry. The real Raft fixture builds the actual shipping executable and exercises bootstrap, repeat/reader rejection, scheduled rotation, nonactivation of future keys, and continued old/new cookie decryption. Coordinated cache refresh, service role activation, production custody, and final integrated cutover remain separate acceptance gates.
