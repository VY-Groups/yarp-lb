# Offline recipient-specific Linux wrapping-key delivery

This is a separately authorized private-key custody operation, NOT part of the encrypted XML snapshot transfer. Use only approved fleet identity, receiver identity, exact externally controlled revision and three independently approved certificate SHA-256 fingerprints. The signer is a dedicated signing leaf, the recipient is a dedicated RSA encryption leaf, and the wrapped PFX is a different key-encipherment leaf. All input files and output roots must be owner-private, absolute, and nonsymlinked. The sender never needs the recipient private key; the receiver never needs the signing private key.

Run `python3 ops/fleet/linux_dp_wrap_delivery.py seal --help` for parameters. Seal accepts the independently pinned signer/receiver certs, signer key, approved wrapping PFX and password file. The output revision directory contains only a CMS DER envelope and a nonsecret receipt. Transfer the opaque envelope via a separately authenticated channel. Open accepts the independently pinned certs, receiver private key, envelope and exact independently approved metadata. It verifies the pinned signer signature first, decrypts the AES-256-GCM/RSA-OAEP-SHA256 envelope, checks the signed recipient/fleet/revision and actual PFX private-key/certificate match, then publishes a new owner-only directory containing wrapper.pfx and wrapper.password. No overwrite; no automatic service config changes. The outer signature is checked against the exact preapproved leaf, not arbitrary embedded certificates. No customer secret is logged or written to CI artifacts.

Never derive the expected revision or trust pins from the received envelope or receipt; keep external approval/rollback floors independently controlled and advance them through the approved lifecycle. The same revision directory cannot be reused. Do not treat a receipt as proof of remote service activation or current quorum. This initial implementation supports currently valid wrapping certificates; historic expired custody remains an independent procedure. Python/OpenSSL process memory may contain private material; deploy under a hardened dedicated account, disable core dumps/swap as appropriate, and use protected filesystem custody. The source and recipient must perform independent operational approvals, escrow, audit and rollback verification. Test coverage uses disposable actual certificates/PFX with distinct recipients and tamper/replay refusal. Full runtime cutover and physical acceptance remain outstanding.
